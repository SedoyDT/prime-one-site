# Безопасность контейнеров

Уровень сложности: ~85/100. Нужен установленный Docker.

**Предполагается:** свободное владение Dockerfile и `docker run` — см. [[dockerfile-i-sborka-obraza|Dockerfile и сборка образа]]. Напоминание из уровня 0–9: контейнер — это изоляция процесса на общем ядре хоста, а не отдельная виртуальная машина; отсюда и следующие правила.

## По умолчанию контейнер — это root

```
docker run --rm alpine whoami
```

Выведет `root`. Это не безобидно: если внутри контейнера есть уязвимость, позволяющая вырваться за пределы изоляции (эскейп), процесс атакующего окажется root-ом на хосте, а не непривилегированным пользователем. Проверить, что процесс контейнера виден с хоста как root:

```
docker run -d --name asroot alpine sleep 300
ps aux | grep "sleep 300"
docker rm -f asroot
```

## Правило 1: непривилегированный пользователь

```dockerfile
FROM alpine:3.20
RUN adduser -D appuser
USER appuser
CMD ["whoami"]
```

```
docker build -t nonroot-demo .
docker run --rm nonroot-demo
```

Выведет `appuser`, не `root`. `USER` — последняя строка перед `CMD`/`ENTRYPOINT`, которая должна применяться: всё, что было до неё (`RUN`, `COPY`), при отсутствии явного `USER` выполняется от root, и это нормально для этапа сборки — важно, кто выполняет **финальный процесс** контейнера.

## Правило 2: read-only файловая система

Если процессу не нужно ничего писать на диск во время работы, файловая система контейнера может быть доступна только для чтения — тогда даже успешный эксплойт не сможет модифицировать файлы образа или подложить свой бинарник:

```
docker run --rm --read-only alpine sh -c "echo test > /tmp/x.txt"
```

Команда провалится с ошибкой `Read-only file system`. Если процессу всё же нужна временная запись (кэш, сокеты) — выдаётся точечный tmpfs, а не полный доступ:

```
docker run --rm --read-only --tmpfs /tmp alpine sh -c "echo test > /tmp/x.txt && cat /tmp/x.txt"
```

Теперь запись в `/tmp` работает, а остальная файловая система по-прежнему read-only.

## Правило 3: лимиты ресурсов

Без лимитов один контейнер может занять всю память или CPU хоста, уронив остальные сервисы:

```
docker run --rm --memory=128m --cpus=0.5 alpine sh -c "echo лимит применён"
```

- `--memory=128m` — если процесс внутри попытается выделить больше, ядро его убьёт (OOM kill внутри контейнера), а не хоста целиком;
- `--cpus=0.5` — контейнер получает не более половины ядра процессорного времени.

В Compose это описывается через ключ `deploy.resources.limits` (или `mem_limit`/`cpus` в старом синтаксисе).

## Правило 4: секреты — не в образе

Частая ошибка:

```dockerfile
# Плохо — пароль остаётся в слое образа навсегда, даже если файл потом удалить
ENV DB_PASSWORD=supersecret
```

Слой с `ENV DB_PASSWORD=supersecret` физически остаётся в истории образа даже после `RUN rm` в следующей инструкции — слои неизменяемы, удаление в новом слое лишь скрывает файл, а не стирает его из предыдущего. Проверить это можно у любого образа:

```
docker history --no-trunc <image>
```

Правильный путь — передавать секреты **при запуске**, не при сборке: `--env-file` (не коммитить сам файл в git), Docker secrets в Swarm-режиме, или менеджер секретов внешней системы (Vault, облачный secret manager). Для сборки, если секрет нужен именно во время `docker build` (например, приватный npm-токен), — `--secret` в BuildKit, который не оставляет значение в итоговых слоях:

```
docker build --secret id=npmtoken,src=./npmtoken.txt -t app .
```

и в Dockerfile: `RUN --mount=type=secret,id=npmtoken cat /run/secrets/npmtoken`.

## Проверка образов на известные уязвимости

```
docker scout quickview <image>
```

(`docker scout` встроен в современный Docker CLI) — покажет известные CVE в базовом образе и его слоях. Практическое следствие: `alpine`/`-slim`-варианты образов не только меньше весят, но и содержат меньше пакетов — а значит, меньше потенциальных уязвимостей для сканирования и патчинга.

## Проверка себя

Возьмите Dockerfile с `USER appuser` из этого туториала, запустите его с `--read-only --memory=64m --cpus=0.5` одновременно и убедитесь через `docker inspect <container> --format '{{.HostConfig.ReadonlyRootfs}} {{.HostConfig.Memory}}'`, что все ограничения реально применились, а не просто были приняты без ошибки.
