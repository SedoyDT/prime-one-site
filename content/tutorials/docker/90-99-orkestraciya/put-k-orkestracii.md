# Путь к оркестрации: от одного хоста ко многим

Уровень сложности: ~95/100 — вершина этой серии, не отдельная тема с нуля. Нужен установленный Docker.

**Предполагается:** весь предыдущий путь — образы, Compose, healthcheck, ограничения ресурсов. Если что-то из этого ещё не пощупано руками, стоит вернуться к [[karta|карте туториалов]] — этот уровень не столько добавляет новую механику Docker, сколько показывает, куда она перестаёт справляться сама.

## Где заканчивается один хост

Всё в этой серии до сих пор работало на одной машине. `docker compose up` поднимает несколько контейнеров, но если машина упадёт — упадёт всё сразу. Если нагрузка вырастет — единственный выход это более мощная машина (вертикальное масштабирование), а не добавление ещё одной. Оркестрация решает три вещи, которые Compose на одном хосте не решает в принципе:

1. **Много хостов** — контейнеры одного приложения распределены по кластеру машин, а не по одной.
2. **Самовосстановление на уровне кластера** — если хост целиком выходит из строя, контейнеры пересоздаются на других хостах автоматически, а не просто перезапускаются на месте (это отличие от `--restart` из уровня 70–79, которое работает только в пределах живого хоста).
3. **Масштабирование по команде** — «нужно не 1 копию сервиса, а 5» превращается в декларативное число, а не в пять раз повторённый `docker run`.

## Docker Swarm — тот же Docker, другой режим

Swarm — встроенный в Docker Engine оркестратор, поэтому проще всего пощупать идею именно через него, а не сразу через Kubernetes (это отдельная, гораздо более объёмная система — освоение начинается уже за пределами этой серии).

Включить режим кластера на одной машине (для реального кластера — те же команды, но `docker swarm join` выполняется ещё и на других хостах):

```
docker swarm init
```

Вывод покажет команду `docker swarm join --token ...` — ей на другие машины добавляются worker-узлы. На одной машине это не нужно, но полезно увидеть, что механизм именно такой: не «настроить конфиг», а присоединить узел к кластеру одной командой.

## Service вместо container

В Swarm-режиме единица управления — не отдельный контейнер, а **service**: декларация «какой образ и сколько копий (реплик) должно работать»:

```
docker service create --name web --replicas 3 -p 8080:80 nginx:alpine
docker service ls
docker service ps web
```

`docker service ps web` покажет три задачи (task) — по одной на реплику, каждая — это обычный контейнер под капотом, но управляемый оркестратором, а не вручную.

## Самовосстановление на практике

```
docker ps
docker rm -f $(docker ps -q --filter name=web)
docker service ps web
```

Ручное убийство контейнера, управляемого сервисом, не уменьшает число реплик — Swarm обнаруживает пропажу и пересоздаёт задачу заново в течение секунд. Это ключевое отличие от `--restart` на уровне одного контейнера: там перезапускается тот же контейнер на том же хосте, здесь — оркестратор поддерживает **декларативное состояние** («должно быть 3 реплики») независимо от того, что произошло с конкретным контейнером или даже целым хостом.

## Масштабирование одной командой

```
docker service scale web=5
docker service ps web
docker service scale web=1
```

Число задач меняется вслед за одной командой — без пересборки, без ручного создания/удаления контейнеров по одному.

## Секреты на уровне кластера

Возвращаясь к правилу «секреты не в образе» из прошлого уровня — Swarm даёт для этого встроенный механизм, отдельный от переменных окружения:

```
echo "supersecret" | docker secret create db_password -
docker service create --name db --secret db_password postgres:16-alpine
```

Секрет монтируется в `/run/secrets/db_password` внутри контейнеров сервиса, никогда не попадает в переменные окружения (которые видны через `docker inspect` всем, у кого есть доступ к демону) и не хранится в самом образе.

## Уборка

```
docker service rm web db
docker secret rm db_password
docker swarm leave --force
```

## Куда дальше за пределами этой серии

Swarm показывает саму идею оркестрации минимальным числом новых понятий поверх того, что уже знакомо по Compose. В индустрии стандартом де-факто стал **Kubernetes** — концептуально те же три задачи (много хостов, самовосстановление, масштабирование), но с гораздо более развитым набором примитивов (Pod, Deployment, Service, Ingress, ConfigMap и десятки других) и собственной экосистемой. Знание из этой серии не пропадает: образы, Dockerfile, healthcheck, безопасность контейнеров — это фундамент, на котором Kubernetes работает точно так же, просто управляет контейнерами не через `docker service`, а через собственный API поверх того же container runtime.

## Проверка себя

Разверните `docker service create --name counter --replicas 2 alpine sleep 3600`, убейте оба контейнера одновременно (`docker rm -f $(docker ps -q --filter name=counter)`), засеките, сколько секунд занимает у Swarm восстановление обеих реплик, и сравните это время с тем, сколько занял бы ручной `docker run` двух новых контейнеров — разница в том, что здесь это произошло без единой команды с вашей стороны.
