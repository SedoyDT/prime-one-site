# Многоэтапная сборка и кэш слоёв

Уровень сложности: ~55/100. Нужен установленный Docker.

**Предполагается:** написан хотя бы один Dockerfile с `FROM`/`RUN`/`COPY`/`CMD` — см. [[dockerfile-i-sborka-obraza|Dockerfile и сборка образа]].

## Каждая инструкция — это слой

`docker build` выполняет Dockerfile построчно, и каждая инструкция (`RUN`, `COPY`, `ADD`) создаёт отдельный неизменяемый слой файловой системы, который кэшируется. Если инструкция и всё, что было до неё, не изменились с прошлой сборки — Docker берёт слой из кэша вместо повторного выполнения.

Проверить на практике:

```dockerfile
FROM alpine:3.20
RUN echo "Собираю в $(date)" > /build-time.txt
CMD ["cat", "/build-time.txt"]
```

```
docker build -t cache-demo .
docker build -t cache-demo .
```

Вторая сборка почти мгновенная и в выводе `docker build` показывает `CACHED` напротив `RUN` — время внутри `/build-time.txt` не изменилось, потому что сам шаг не выполнялся повторно.

## Порядок инструкций решает всё

Кэш инвалидируется с той инструкции, где что-то реально изменилось, и **всех последующих** — даже если они сами не менялись. Отсюда правило: то, что меняется реже, должно стоять раньше в Dockerfile.

Плохой порядок (типичная ошибка):

```dockerfile
FROM node:20-alpine
COPY . .
RUN npm install
CMD ["node", "server.js"]
```

Любое изменение любого файла проекта (`COPY . .`) инвалидирует кэш `npm install` — зависимости будут переустанавливаться на каждую правку `server.js`, даже если `package.json` не менялся.

Хороший порядок:

```dockerfile
FROM node:20-alpine
COPY package.json package-lock.json ./
RUN npm install
COPY . .
CMD ["node", "server.js"]
```

Теперь `npm install` кэшируется, пока не поменялся именно `package.json`/`package-lock.json` — правка кода в `server.js` пересобирает только последний слой.

## `.dockerignore`

`COPY . .` копирует контекст сборки как есть — включая `node_modules`, `.git`, локальные логи, если не сказано иначе. `.dockerignore` (синтаксис как у `.gitignore`) исключает их:

```
node_modules
.git
*.log
```

Это не только ускоряет сборку (меньше данных передаётся демону Docker), но и предотвращает случайное попадание в образ файлов, которые не должны там быть — вплоть до `.env` с секретами.

## Многоэтапная сборка

Инструменты для сборки (компиляторы, полный набор зависимостей) не нужны в финальном образе — там нужен только результат. Многоэтапная сборка решает это явно, на примере компиляции Go-программы:

`main.go`:
```go
package main

import "fmt"

func main() {
	fmt.Println("Собран многоэтапно")
}
```

`Dockerfile`:
```dockerfile
# Этап 1: сборка — здесь нужен весь Go-тулчейн
FROM golang:1.22-alpine AS builder
WORKDIR /src
COPY main.go .
RUN go build -o app main.go

# Этап 2: финальный образ — только результат
FROM alpine:3.20
COPY --from=builder /src/app /app
CMD ["/app"]
```

```
docker build -t multistage-demo .
docker run --rm multistage-demo
```

`COPY --from=builder` берёт файл не с диска хоста, а из файловой системы **другого этапа сборки**. Финальный образ не содержит ни Go-компилятора, ни исходников — только бинарник и Alpine. Сравните размеры:

```
docker images | grep -E "golang|multistage-demo"
```

Разница обычно на порядок — сотни мегабайт у `golang:1.22-alpine` против единиц-десятков мегабайт у `multistage-demo`.

## Проверка себя

Возьмите Dockerfile из этого туториала, добавьте между `FROM golang` и `COPY main.go .` строку `RUN echo "не влияет на кэш ниже"`, пересоберите дважды и убедитесь по выводу `docker build`, что: (1) новая `RUN` выполнилась один раз и закэшировалась при повторной сборке, (2) добавление строки **выше** `COPY main.go .` не сломало кэш этой и предыдущих команд, потому что раньше её ничего не менялось.
