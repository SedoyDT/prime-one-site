# Docker-сети: как контейнеры находят друг друга

Уровень сложности: ~45/100. Нужен установленный Docker.

**Предполагается:** уверенное обращение с `docker run`, `-p`, `-e` — см. [[konteynery-dannye-i-peremennye|Управление контейнерами]].

## Три встроенных сети

```
docker network ls
```

Покажет минимум три сети, которые Docker создаёт сам:

- **bridge** (сеть по умолчанию) — виртуальный коммутатор на хосте; каждый контейнер получает свой IP в этой сети; это то, что используется, если не указать `--network` явно.
- **host** — контейнер использует сетевой стек хоста напрямую, без изоляции портов (нет нужды в `-p`, но и нет изоляции).
- **none** — контейнер вообще без сети.

## Проблема сети по умолчанию

```
docker run -d --name db1 alpine sleep 3600
docker run -d --name db2 alpine sleep 3600
docker exec db2 ping -c 2 db1
```

Последняя команда провалится с ошибкой разрешения имени. Сеть `bridge` по умолчанию не даёт контейнерам находить друг друга по имени — только по IP, который вдобавок каждый раз новый. Это устаревшее поведение, оставленное для обратной совместимости.

## Решение: своя сеть

```
docker network create my-net
docker rm -f db1 db2
docker run -d --name db1 --network my-net alpine sleep 3600
docker run -d --name db2 --network my-net alpine sleep 3600
docker exec db2 ping -c 2 db1
```

Теперь `ping` проходит. Разница единственная — `--network my-net` вместо сети по умолчанию: **любая пользовательская сеть** в Docker включает встроенный DNS, где имя контейнера (или его `--name`, если задан) автоматически резолвится в текущий IP. Это и есть базовый механизм, на котором строится Docker Compose (следующие уровни) — там сеть создаётся автоматически, а сервисы обращаются друг к другу просто по имени.

## Практический пример: nginx перед приложением

```
docker network create app-net

docker run -d --name backend --network app-net alpine sh -c \
  "while true; do echo -e 'HTTP/1.1 200 OK\n\nПривет из backend' | nc -l -p 5000; done"

docker run -d --name frontend --network app-net -p 8080:80 nginx:alpine
docker exec frontend sh -c "wget -qO- http://backend:5000"
```

`frontend` достучался до `backend` по имени контейнера, хотя порт 5000 у `backend` никуда не пробрасывался на хост (`-p` не указан) — обращение изнутри сети `app-net` не требует публикации порта наружу. Публикация через `-p` нужна только для доступа снаружи Docker-сети (с хоста или из интернета).

Уборка:

```
docker rm -f backend frontend db1 db2
docker network rm my-net app-net
```

## Изоляция сетей друг от друга

Контейнеры в разных пользовательских сетях друг друга не видят, даже если оба на одном хосте — это встроенная сегментация:

```
docker network create net-a
docker network create net-b
docker run -d --name a1 --network net-a alpine sleep 3600
docker run -d --name b1 --network net-b alpine sleep 3600
docker exec a1 ping -c 1 b1
```

`ping` не пройдёт — `a1` и `b1` в разных сетях. Подключить контейнер сразу к нескольким сетям можно через `docker network connect`.

## Проверка себя

Создайте сеть `demo-net`, поднимите в ней `redis:alpine` без публикации портов и второй контейнер `alpine` с установленным `redis-cli` (образ `alpine` его не содержит — вместо этого можно проверить связь через `nc -zv redis 6379`, где `redis` — имя контейнера с Redis). Убедитесь, что порт открыт по имени контейнера, но недоступен с хоста напрямую (`curl localhost:6379` не должен сработать без `-p`).
