# Управление контейнерами: данные, порты, переменные окружения

Уровень сложности: ~35/100. Нужен установленный Docker.

**Предполагается:** умение собрать и запустить образ по своему Dockerfile — [[dockerfile-i-sborka-obraza|Dockerfile и сборка образа]].

## Проблема: контейнер забывает всё

Запустите и измените файл внутри контейнера:

```
docker run --name test1 -it alpine sh
echo "важные данные" > /data.txt
exit
```

Контейнер остановлен, но не удалён (без `--rm`). Запустите его заново тем же именем:

```
docker start -ai test1
cat /data.txt
exit
```

Файл на месте — потому что это **тот же** контейнер, просто снова запущенный (`docker start`, не `docker run`, — `run` создал бы новый). А теперь:

```
docker rm test1
```

Данные исчезли безвозвратно вместе с контейнером. Это ожидаемое поведение: файловая система контейнера — часть его жизненного цикла, а не отдельное хранилище.

## Решение: тома (volumes)

Именованный том — область на диске хоста, управляемая Docker'ом, которая живёт отдельно от любого конкретного контейнера:

```
docker volume create my-data
docker run --rm -v my-data:/data alpine sh -c "echo 'сохранюсь' > /data/note.txt"
docker run --rm -v my-data:/data alpine cat /data/note.txt
```

Два разных контейнера (каждый со своим `--rm`, то есть удаляется сразу после работы) видят один и тот же файл — потому что `/data` внутри каждого из них указывает на один и тот же том `my-data`, а не на файловую систему контейнера.

Список и удаление томов:

```
docker volume ls
docker volume rm my-data
```

## Bind mount: прямой доступ к папке хоста

Вместо тома, которым управляет Docker, можно напрямую примонтировать папку с диска хоста — удобно для разработки, когда код меняется на хосте, а исполняется в контейнере:

```
mkdir -p ~/docker-demo && echo "hello" > ~/docker-demo/file.txt
docker run --rm -v ~/docker-demo:/app alpine cat /app/file.txt
```

Отличие от именованного тома: `-v <путь-на-хосте>:<путь-в-контейнере>` вместо `-v <имя-тома>:<путь>`. Изменения видны в обе стороны немедленно, без пересборки образа.

## Порты: достучаться до контейнера снаружи

Контейнер по умолчанию изолирован по сети — снаружи хоста к нему не достучаться. Проброс порта открывает конкретную дверь:

```
docker run --rm -d -p 8080:80 --name web nginx:alpine
curl http://localhost:8080
docker stop web
```

- `-d` (detach) — запустить в фоне, не занимая терминал;
- `-p 8080:80` — порт 8080 на хосте перенаправляется на порт 80 внутри контейнера (это порт, на котором nginx слушает по умолчанию).

## Переменные окружения

Многие образы настраиваются через переменные окружения вместо правки файлов:

```
docker run --rm -e GREETING="Привет, Docker" alpine sh -c 'echo $GREETING'
```

Для набора переменных удобнее файл, чем длинная цепочка `-e`:

`.env`:
```
GREETING=Привет из файла
LANG=ru_RU.UTF-8
```

```
docker run --rm --env-file .env alpine sh -c 'echo $GREETING'
```

## Наблюдение за живыми контейнерами

Набор команд, который понадобится постоянно:

```
docker ps                    # запущенные контейнеры
docker logs web               # вывод контейнера (stdout/stderr)
docker exec -it web sh        # зайти внутрь УЖЕ работающего контейнера
docker stop web                # мягкая остановка (SIGTERM, потом SIGKILL)
docker rm web                  # удалить остановленный контейнер
```

Разница `docker run -it` и `docker exec -it`: `run` создаёт новый контейнер, `exec` открывает ещё один процесс внутри уже существующего и работающего.

## Проверка себя

Запустите `nginx:alpine` с проброшенным портом и с bind-mount своей папки на `/usr/share/nginx/html` (это папка, откуда nginx отдаёт статику), положите туда `index.html` со своим текстом и убедитесь через `curl`, что отдаётся именно он, а не страница nginx по умолчанию.
