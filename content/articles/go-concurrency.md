# Конкурентность в Go — каналы, синхронизация и типичные баги

Конкурентность в Go выглядит просто: `go f()`, каналы, `sync.WaitGroup`. Но большинство багов здесь — не про синтаксис, а про модель: что гарантировано, что нет, и когда «работает на моей машине» означает «гонка, которая пока не проявилась». Разберём модель и самые частые способы на ней подорваться.

## Горутины: что `go` гарантирует, а что нет

`go f()` только **планирует** горутину к выполнению. Она может начать исполняться в любой момент — или вообще не начать, если основная горутина завершится раньше. Порядок запуска не гарантирован ничем.

```go
func main() {
    go fmt.Println("hello") // может не напечататься никогда
}
```

`main()` — тоже горутина. Как только она завершается, программа завершается целиком, не дожидаясь остальных. Если `main` выходит раньше, чем запланированная горутина получила процессорное время, вывода не будет.

По стоимости горутина несопоставима с потоком ОС: стартовый стек — несколько КБ (растёт динамически), против 1–8 МБ у потока ОС. Сотни тысяч горутин — нормально; столько потоков ОС создать нельзя.

**Переменная цикла (до Go 1.22).** Классическая ловушка:

```go
for i := 0; i < 5; i++ {
    go func() { fmt.Println(i) }() // печатает пять пятёрок
}
```

До Go 1.22 `i` была одна на весь цикл, общая для всех замыканий. К моменту, когда горутины реально выполнятся, цикл завершён и `i == 5` у всех. Лечилось передачей параметром (`go func(i int){...}(i)`) или копией в теле цикла. В Go 1.22+ переменная цикла своя на каждую итерацию — но код, рассчитанный на старое поведение, встречается до сих пор.

## Каналы

Философия: **«не общайся через разделяемую память — разделяй память через общение»**. Канал передаёт владение данными между горутинами явно, а не защищает одновременный доступ. Это другая модель, чем мьютекс, а не просто другой синтаксис.

### Небуферизованный канал: рандеву

```go
ch := make(chan int)
ch <- 5 // блокируется, пока кто-то не выполнит <-ch
```

Отправка и приём синхронизированы: отправитель стоит, пока получатель не заберёт значение. Это даёт гарантию — когда `ch <- 5` вернул управление, получатель **точно** уже принял. Если нужно подтверждение, что получатель реально начал обработку (а не просто положил сообщение в очередь), — только небуферизованный канал.

### Буферизованный канал

```go
ch := make(chan int, 3)
ch <- 1 // не блокируется: в буфере есть место
```

Блокировка наступит на попытке записать в полный буфер. Тонкость: наличие в коде читающей горутины **не** гарантирует, что она исполняется прямо сейчас. Программа с буфером на 10 может зависнуть на 11-й отправке, если читатель ещё не запущен или сам заблокирован на чём-то другом.

### Закрытие

- `v, ok := <-ch`, где `ok == false` — канал закрыт и все буферизованные значения вычитаны. Дальше будут только нулевые значения типа.
- `for v := range ch` завершается сам, когда канал закрыт и опустошён. В отличие от `range` по слайсу, длина заранее неизвестна — сигнал окончания даёт именно `close`.
- `close(ch)` дважды — **паника** `close of closed channel`.
- Запись в закрытый канал (`ch <- 5` после `close`) — **паника** `send on closed channel`, независимо от наличия читателей.

Отсюда правило: **закрывает канал только один владелец** — обычно единственный производитель или отдельная координирующая горутина, дождавшаяся всех. Если производителей несколько и каждый может закрыть канал, остальные при следующей записи запаникуют.

### nil-канал

```go
var ch chan int
<-ch // блокируется навсегда, не паникует
```

Чтение и запись в nil-канал не паникуют, а блокируются бесконечно — частая причина «тихого» зависания. Но у этого есть полезное применение в `select` (ниже).

## select

```go
select {
case v := <-ch1: // ...
case v := <-ch2: // ...
}
```

- Если готовы несколько case — выбирается **случайный** из готовых, не по порядку в коде.
- `case <-time.After(5*time.Second):` — таймаут ожидания вместо бесконечной блокировки.
- `default:` делает `select` **неблокирующим**: если ни один case не готов немедленно, выполняется `default`. Без `default` тот же `select` ждал бы.
- Присвоить переменной канала `nil` — способ временно «выключить» ветку: nil-канал в `select` никогда не готов и никогда не выбирается, структуру `select` менять не нужно.

## Примитивы синхронизации

### sync.Mutex / RWMutex

Мьютекс — прямой инструмент для защиты доступа к разделяемым данным на месте, без передачи владения через канал. Для простого счётчика часто проще канала.

- **Не реентерабелен.** `mu.Lock()` дважды подряд из одной горутины без промежуточного `Unlock()` (например, в рекурсии) — **deadlock**: повторный `Lock()` ждёт освобождения, которое должна была сделать сама же горутина.
- **RWMutex** — когда структура читается часто и параллельно, а пишется редко. Много читателей держат `RLock()` одновременно; `Lock()` блокирует только на время реальной записи. Обычный `Mutex` сериализовал бы даже параллельные чтения.

### sync.WaitGroup

- `wg.Add(1)` вызывать **до** запуска горутины, а не внутри неё. Иначе `wg.Wait()` в другом месте может выполниться раньше, чем счётчик увеличится, и вернуть управление преждевременно.
- Лишний `wg.Done()` — **паника** `sync: negative WaitGroup counter`.
- `wg.Wait()` висит вечно, хотя все горутины «по логам завершились» — почти всегда число `Add` не сошлось с числом `Done`: неверный аргумент `Add(n)` или горутина упала паникой до `defer wg.Done()`.

### sync.Once

`sync.Once.Do(f)` гарантирует ровно одно выполнение `f`, даже при параллельных вызовах. Наивное `if instance == nil { instance = create() }` не потокобезопасно: несколько горутин могут пройти проверку `nil` до первого присваивания.

Важная деталь: если `f` внутри `once.Do` **паникует**, вызов всё равно считается состоявшимся. Повторные `Do()` никогда больше не выполнят `f`, даже после неудачной первой попытки.

### sync/atomic

Атомарные операции — на уровне отдельных процессорных инструкций, без Lock/Unlock. Для инкремента одного счётчика заметно быстрее мьютекса. Но защищают ровно **одно** значение за раз: согласованное изменение нескольких полей как транзакции (например, обновить и `min`, и `max`) требует мьютекса на всё обновление.

## context.Context — распространение отмены

`context.Context` первым аргументом почти в каждую функцию с сетевым вызовом или долгой операцией — это стандартный механизм пробросить сигнал отмены и дедлайн через всю цепочку вызовов. Функция периодически проверяет `ctx.Done()` и прекращает работу, если вызывающий код отменил операцию или истёк таймаут.

- `context.WithCancel` — даёт функцию `cancel()`, которую код вызывает явно по бизнес-логике.
- `context.WithTimeout` (обёртка над `WithDeadline`) — отменяет контекст автоматически по истечении времени.
- `context.Background()` — корневой контекст для реального кода (main, инициализация, тесты). `context.TODO()` — временная заглушка «сюда нужно будет добавить контекст, но пока неясно откуда».
- **Анти-паттерн:** строковый ключ в `context.WithValue(ctx, "userID", 42)`. Ключи из разных пакетов могут совпасть и подменить значение. Идиома — приватный тип-ключ: `type ctxKey int`.

Практический сценарий: HTTP-хендлер породил несколько горутин для параллельных запросов к другим сервисам, клиент оборвал соединение. Без `ctx.Done()` внутри этих горутин они продолжат работу вхолостую до естественного завершения, тратя ресурсы на никому не нужный результат. Context — единственный штатный способ распространить отмену вниз по дереву горутин.

## Гонки данных

`go run -race` компилирует программу с инструментацией всех обращений к памяти из разных горутин и сообщает о гонках в рантайме. Не включён по умолчанию из-за накладных расходов: память 5–10×, время 2–20×.

Ключевое ограничение: race detector находит только гонки, **реально произошедшие** при конкретном чередовании горутин в конкретном прогоне. Недетерминированный планировщик может не воспроизвести проблемное чередование в тесте — даже если тесты в CI детерминированы и всегда проходят с `-race`, это **не** доказывает отсутствие гонки в коде.

И «на практике никогда не было проблем» — не аргумент оставить несинхронизированный доступ. Гонка данных — undefined behavior в модели памяти Go: оптимизации компилятора в следующей версии могут проявить баг, который раньше случайно маскировался порядком выполнения.

## Deadlock

```go
func main() {
    ch := make(chan int)
    ch <- 1 // fatal error: all goroutines are asleep - deadlock!
}
```

Планировщик отслеживает, что **все** существующие горутины заблокированы одновременно и прогресс в принципе невозможен — тогда рантайм завершает программу с диагностикой, а не висит бесконечно. (Это работает только когда заблокированы *все*; одна зависшая горутина при живых остальных так не ловится.)

Классический взаимный deadlock — захват блокировок в разном порядке:

- горутина A: `mu1.Lock()`, затем `mu2.Lock()`;
- горутина B: `mu2.Lock()`, затем `mu1.Lock()`.

A держит `mu1` и ждёт `mu2`, B держит `mu2` и ждёт `mu1`. Решение — всегда захватывать несколько блокировок в едином, согласованном по всей кодовой базе порядке (lock ordering).

## Утечки горутин

Утечка горутины — горутина, заблокированная навсегда (например, на отправке в канал, который никто больше не читает). GC не может собрать её стек и ресурсы, пока горутина технически «жива», даже если она никогда не продолжит выполнение.

Симптом на проде: сервис со временем ест всё больше памяти при стабильном потоке запросов, `pprof` показывает растущее число горутин. Искать в первую очередь — горутины, порождённые на каждый запрос, которые блокируются на канале или мьютексе **без таймаута/отмены** и не завершаются, если читатель уже ушёл (клиент отключился, вызывающий код вернулся раньше).

`go sendMetric(data)` без ожидания — типичный источник: горутина живёт, пока не закончится её функция; блокирующий сетевой вызов без deadline внутри может подвесить её бессрочно, и такие горутины тихо накапливаются при частых вызовах.

Особо коварный случай: `wg.Wait()` внутри HTTP-хендлера ждёт группу фоновых горутин, одна из которых заблокирована на канале, который никто не закроет. Хендлер зависнет вместе со всем запросом — `wg.Wait()` без таймаута/context блокируется, пока **все** не вызовут `Done()`, и одна зависшая горутина держит весь `WaitGroup`.

## Паттерны

**Worker pool** — фиксированное число горутин читает задачи из общего канала. Ограничивает потребление ресурсов (стеки, подключения к внешним системам, конкуренция за CPU): при огромном потоке задач запуск горутины на каждую исчерпает ресурсы быстрее, чем задачи обрабатываются.

**Fan-out / fan-in** — несколько горутин параллельно читают из одного входного канала, результаты сливаются в один выходной. На стадии fan-in выходной канал должен закрываться **только после того, как все worker-горутины завершили запись** — обычно через `sync.WaitGroup`, дождавшись которого отдельная горутина закрывает выходной канал. Иначе потеря данных или паника записи в закрытый канал.

**Pipeline** — цепочка стадий, каждая читает из канала предыдущей и пишет в канал следующей. Каждая стадия обязана закрыть **свой** выходной канал, когда входной закрылся и данные обработаны. Промежуточная стадия, которая этого не делает, подвесит следующую в `range` навсегда.

**Семафор из буферизованного канала** — ограничить число одновременных обращений к внешнему API без полноценного пула:

```go
sem := make(chan struct{}, N)
sem <- struct{}{}        // занять слот (блокируется, если все N заняты)
defer func() { <-sem }() // освободить
```

Неблокирующий вариант «занято — сразу ошибка»:

```go
select {
case sem <- struct{}{}: // слот занят
default:                 // слотов нет, не ждём
}
```

**Таймаут с остановкой производителя.** `time.After` в `select` у потребителя лишь перестаёт ждать сам — производитель продолжит работать вхолостую. Чтобы производитель тоже завершился, нужен `context.WithTimeout`, переданный ему: по истечении срока context отменяется, и производитель (если проверяет `ctx.Done()`) останавливается.

## Что унести с собой

- `go f()` ничего не гарантирует про порядок и факт запуска; `main` завершилась — программа завершилась.
- Небуферизованный канал = рандеву (синхронизация), буферизованный = очередь (развязка). Закрывает — один владелец.
- Каналы и мьютексы решают одну задачу разными моделями; atomic — только для одиночного значения.
- `-race` находит проявившуюся гонку, а не доказывает её отсутствие.
- Почти каждая утечка горутины — блокировка на канале/мьютексе без таймаута и без `ctx.Done()`.

Тот же принцип «модель прежде команд» — в разборе [[git-internals]] и в туториалах [[ripgrep]] и [[jq]].
