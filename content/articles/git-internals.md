# Git изнутри — объектная модель, ссылки и восстановление

Git кажется набором разрозненных команд, пока не увидишь модель под ними. А модель маленькая: четыре типа объектов, несколько текстовых файлов со ссылками и одно правило адресации. Почти всё поведение Git — от дедупликации файлов до `git bisect` — следствие этих трёх вещей. Разберём их по порядку.

## Content-addressable storage

Git — это хранилище с адресацией по содержимому. Каждый объект (blob, tree, commit, tag) адресуется хешем собственного содержимого, а не произвольным именем, которое ему кто-то присвоил. Одинаковое содержимое всегда даёт один и тот же адрес.

Из одного этого правила follows сразу несколько практических свойств:

- **Встроенная дедупликация.** Два файла с идентичным содержимым, но разными именами, в одном коммите породят **один** blob-объект — имя файла хранится не в blob, а в tree. Случайно скопировали файл в три места репозитория? Объектная база не раздувается: физически blob лежит один раз, на него просто ссылаются три записи в tree.
- **Переименование не создаёт новый объект.** Хеш blob зависит только от байтов содержимого. Переименовали файл, не тронув содержимое, — blob остался тем же, изменилась лишь запись в tree (новое имя, тот же хеш). Git вообще не хранит операцию «переименование» как факт; `git log --follow` восстанавливает её эвристически, по сходству содержимого.
- **Целостность.** Изменение содержимого автоматически меняет адрес. Подменить объект незаметно нельзя — адрес перестанет сходиться.

Исторически адрес — это SHA-1, в новых версиях идёт переход на SHA-256. Причём дело не в случайных коллизиях (их вероятность для обычных данных ничтожна), а в том, что для SHA-1 коллизии **сконструированы целенаправленно**. Для системы, которая гарантирует целостность кода, опираться на алгоритм с продемонстрированными коллизиями принципиально нельзя.

## Четыре типа объектов

### blob

Хранит содержимое файла — только байты, без имени, без прав доступа, без метаданных.

### tree

Описывает структуру каталога: список записей, в каждой — режим доступа, тип, хеш и имя. Tree ссылается на blob'ы для файлов и на другие tree — для подкаталогов. Рекурсивно это описывает всё дерево проекта на момент снимка.

Отдельный случай — **gitlink**: запись вида `160000 commit <хеш>` внутри tree. Так хранится подмодуль. Родительский репозиторий не держит содержимого подмодуля — только указатель на конкретный коммит другого, самостоятельного репозитория. Отсюда типичная ловушка: разработчик закоммитил изменения *внутри* подмодуля, но забыл `git add` в родителе. Коллеги, склонировавшие родительский репозиторий, получат подмодуль на **старом** зафиксированном коммите — обновление gitlink требует отдельного явного коммита в родителе.

### commit

Помимо ссылки на корневой tree (снимок всего проекта), commit хранит:

- **ссылку(и) на родителя** — ноль для первого коммита, один в обычном случае, два и больше у merge-коммита;
- **author** — кто и когда написал изменение;
- **committer** — кто и когда применил коммит (расходится с author при cherry-pick, rebase, применении патчей);
- **сообщение**.

Почему в хеш коммита входит хеш родителя, а не только хеш tree? Потому что это связывает коммит с конкретным местом в истории. Тот же tree (то же содержимое проекта), но с другим родителем — это другой коммит-объект. Именно поэтому история — криптографически связанная цепочка: измени любой давний коммит, и хеши всех его потомков поедут следом. Переписать историю «тихо» невозможно.

Merge-коммит — единственный тип с более чем одним родителем. Он хранит вершины **обеих** сливаемых веток на момент слияния, формально сводя два независимых пути истории в один узел графа.

### tag (annotated)

Именованный объект-обёртка над коммитом с собственным сообщением и подписью. Лёгкий тег — это просто ссылка (см. ниже), объекта не создаёт.

## `.git/` — это вся база, а не кеш

Внутри `.git/` физически лежит всё: `objects/` (blob/tree/commit), `refs/` (ветки и теги), `config` (локальная конфигурация). Отдельного «файла истории» не существует — история **это и есть** граф commit-объектов внутри `objects/`.

Практический вывод жёсткий: удалили каталог `.git/`, оставив рабочие файлы, — вся история, ветки, теги и сама принадлежность к Git уничтожены безвозвратно. Рабочие файлы остаются обычными файлами на диске, проект перестаёт быть репозиторием.

## Ссылки: HEAD, ветки, навигация

Ветка — это текстовый файл с одним хешем коммита. Ничего больше. «Передвинуть ветку» = переписать этот файл.

`.git/HEAD` в обычном состоянии — тоже текстовый файл, с содержимым вида `ref: refs/heads/main`. Это **символическая ссылка на ссылку**, не прямой хеш. Когда вы коммитите, Git читает `HEAD`, разыменовывает до конкретного `refs/heads/<имя>`, узнаёт хеш последнего коммита ветки и обновляет именно этот файл ветки. Вся навигация «где я сейчас» строится через один файл `HEAD`.

**Detached HEAD** — состояние после `git checkout <хеш-коммита>` напрямую (не по имени ветки). Теперь в `.git/HEAD` записан хеш, а не символическая ссылка. Новые коммиты в этом состоянии не двигают вперёд никакую ветку и рискуют стать недостижимыми после переключения на другую ветку — если явно не сохранить их под именем (`git branch спасательная-ветка <хеш>`).

### Навигация по предкам: `~` против `^`

- `HEAD~2` — второй предок по **первой** родительской линии (дедушка, эквивалент `HEAD~1~1`).
- `HEAD^2` — **второй родитель** самого HEAD. Осмысленно только для merge-коммитов.

`git show HEAD^2` выдаёт ошибку или «не тот» коммит — почти всегда потому, что HEAD не merge-коммит, и второго родителя у него просто нет.

## Индекс (staging area)

`git add file` — это не только изменение того, что покажет `git status`. Git **сразу** создаёт blob-объект из содержимого файла и записывает его хеш в `.git/index`. Объект попадает в базу данных уже на этапе `add`, задолго до коммита.

Отсюда неочевидное поведение: добавили файл в staging, затем изменили его на диске ещё раз без повторного `git add` — в коммит попадёт **версия из первого `add`**. Index хранит зафиксированный снимок содержимого (уже созданный blob), а не ссылку на живой файл.

Зачем вообще отдельный буфер между рабочей директорией и коммитом? Чтобы собрать коммит из **части** изменённых файлов — или даже из части изменений одного файла через `git add -p`. Промежуточный слой даёт явный контроль над тем, что именно уйдёт в следующий снимок истории.

## Слияние: fast-forward против merge-коммита

`git merge feature` выполняется как **fast-forward**, когда `main` является прямым предком `feature` в графе — то есть в `main` нет ни одного коммита, которого нет в `feature`. Тогда Git не создаёт новый коммит вообще: он просто передвигает ссылку `main` вперёд, на коммит `feature`.

Тот же `git merge feature` в другой раз создаёт merge-коммит с двумя родителями — потому что после расхождения веток в `main` появились собственные коммиты, отсутствующие в `feature`. Простое перемещение ссылки стёрло бы их; Git создаёт merge-коммит, объединяющий оба пути.

`git merge --no-ff` заставляет создать merge-коммит даже там, где fast-forward технически возможен. Смысл — сохранить в истории явный факт, что сливалась отдельная ветка: при fast-forward её коммиты растворяются в линейной истории `main` без видимой границы.

## Восстановление потерянного

После `git reset --hard` коммиты «пропадают» — ветка теперь указывает на более ранний коммит, и до прежней вершины не добраться по обычным ссылкам. Но объект ещё физически в базе. Цепочка восстановления:

1. **reflog** сохраняет прежнее положение ветки — `git reflog` покажет, куда она указывала до reset.
2. **`git fsck --dangling`** находит «висящие» объекты: коммиты, blob'ы, tree, до которых нельзя добраться ни от одной ветки, тега или другой достижимой ссылки, но которые ещё не удалены.
3. Пока **`git gc`** не выполнит реальную сборку мусора (по умолчанию отсрочка порядка двух недель, но настройки и отдельные операции могут ускорить), объект восстановим. После настоящего gc — удалён безвозвратно.

Именно поэтому `git fsck --dangling` находит коммит, потерянный несколько часов назад, но не находит потерянный неделю назад: между этими событиями, скорее всего, прошёл gc.

## `git bisect` — бинарный поиск по графу

`git bisect` находит коммит, внёсший баг, за логарифмическое число шагов вместо линейного перебора всей истории. Алгоритм — бинарный поиск между известной «хорошей» и «плохой» точками: на каждом шаге проверяется коммит примерно посередине оставшегося диапазона, и по результату (`good`/`bad`) диапазон сокращается вдвое.

`git bisect run <скрипт>` автоматизирует цикл: скрипт сам собирает и тестирует каждый предложенный коммит, возвращая код завершения (0 — хороший, ненулевой — плохой), а `bisect` продолжает сужение без ручного вмешательства.

Между шагами `bisect` оставляет репозиторий в detached HEAD — и это безопасно, в отличие от обычного риска detached HEAD. Причина: `bisect` не создаёт новых коммитов, он лишь переключает HEAD между уже существующими, полностью достижимыми через историю коммитами. Риск потери актуален только для **новых** коммитов поверх detached-состояния.

## Удалённые репозитории: shallow, partial, sparse

`git clone --depth 1` скачивает только последний коммит — снимок tree/blob на текущий момент, без объектов родительских коммитов. `git log` в таком клоне покажет один коммит, хотя в оригинале их тысячи, — это не баг, а прямое следствие: истории попросту нет в локальной базе. Полную историю добирают через `git fetch --unshallow`.

Если нужен только один подкаталог большого монорепозитория, **но с полной историей по нему**, shallow clone не подходит — он обрезает именно историю. Здесь работает связка:

- **partial clone** (`--filter=blob:none`) — откладывает скачивание содержимого blob'ов до реального обращения к файлу;
- **sparse-checkout** — ограничивает рабочую директорию нужным подкаталогом.

История коммитов при этом остаётся полной.

## Что стоит унести с собой

- Всё содержимое адресуется хешем содержимого — отсюда дедупликация, дешёвые переименования и криптографическая связность истории.
- Ветка — файл с хешем; HEAD — файл со ссылкой на ветку; переключение и коммит — это переписывание этих файлов.
- `git add` материализует blob немедленно, в коммит идёт снимок на момент add.
- «Потерянные» коммиты живут в объектной базе до `git gc`; reflog + `fsck --dangling` их находят.
- `.git/` — вся база целиком, а не вспомогательный кеш.

Подход, который окупается и здесь, и в других инструментах: сначала модель, потом команды. В том же ключе разобраны [[go-concurrency]] и практические туториалы [[ripgrep]] и [[jq]].
