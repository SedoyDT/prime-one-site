# Docker изнутри — слои, образы и что на самом деле изолировано

Docker обычно объясняют через команды: `build`, `run`, `push`. Но большинство неожиданностей — «образ весит гигабайт непонятно почему», «закешировался не тот слой», «контейнер видит чужие процессы» — понятны сразу, если знать три вещи: как устроены слои образа, чем контейнер отличается от образа и что именно изолирует Linux-ядро, а что нет.

## Образ — это стопка слоёв, а не файл

Docker-образ — не единый архив, а последовательность read-only слоёв, наложенных друг на друга через union filesystem (в современном Docker — обычно overlay2). Каждая инструкция `Dockerfile`, которая меняет файловую систему (`RUN`, `COPY`, `ADD`), создаёт новый слой поверх предыдущего.

```dockerfile
FROM node:20-slim     # слой 1..N (базовый образ — тоже стопка слоёв)
COPY package.json .   # новый слой: один файл
RUN npm install        # новый слой: node_modules
COPY . .               # новый слой: остальной код
```

Слои кешируются по хешу инструкции и содержимого. Если `package.json` не менялся, `RUN npm install` возьмётся из кеша — именно поэтому `COPY package.json .` идёт отдельной строкой до `COPY . .`: любое изменение кода не должно инвалидировать слой с зависимостями. Поменяли местами — и `npm install` перевыполняется на каждый чих в коде.

Слой, который что-то удаляет (`RUN rm -rf ...`), не уменьшает образ. Он лишь добавляет сверху запись «этого файла больше нет» (whiteout-файл в overlay2). Байты предыдущего слоя остаются физически в образе. Файл, случайно записанный и удалённый в двух разных слоях, продолжает занимать место — отсюда совет объединять `RUN` в одну инструкцию, если внутри неё что-то создаётся и тут же чистится.

## Образ vs контейнер

Образ — read-only шаблон. Контейнер — образ плюс один тонкий read-write слой сверху (thin writable layer) и собственный процесс. Отсюда прямые следствия:

- **Один образ — много контейнеров.** Слои образа переиспользуются между всеми контейнерами, запущенными из него; физически на диске они не дублируются.
- **Данные контейнера эфемерны.** Всё, что процесс написал в свой writable-слой, исчезает при `docker rm`. `docker stop` / `docker start` этот слой сохраняют — удаляет именно `rm`.
- **`docker commit`** запечатывает writable-слой контейнера в новый read-only слой образа — механически то же самое, что делает `RUN` при сборке, только руками и без Dockerfile.

Отсюда правило: для данных, которые должны пережить контейнер (БД, аплоады), writable-слой не подходит — нужен volume или bind mount, которые физически лежат вне слоёв образа и просто монтируются в файловую систему контейнера.

## Что изолирует контейнер, а что — нет

Контейнер — это не виртуальная машина. Ядро одно на хост и все контейнеры; изоляция обеспечивается двумя механизмами Linux:

- **namespaces** — каждый контейнер получает собственное пространство имён для PID, сети, точек монтирования, hostname и т.д. Поэтому `ps` внутри контейнера видит только свои процессы, а не все процессы хоста.
- **cgroups** — ограничивают и учитывают ресурсы (CPU, память) для группы процессов контейнера.

Чего это не даёт:

- **Ядро общее.** Уязвимость в ядре хоста потенциально доступна из контейнера — в отличие от VM, где гостевое ядро изолировано гипервизором.
- **root в контейнере по умолчанию — root на хосте** (тот же UID 0), если явно не настроены user namespaces или `USER` в Dockerfile. Процесс, вырвавшийся за пределы контейнерной изоляции, действует с правами root на хосте.
- **Архитектура процессора не эмулируется.** `docker run --platform linux/amd64` на ARM-хосте работает только через эмуляцию (QEMU) и заметно медленнее — контейнер не «виртуализирует» CPU, он использует хостовый напрямую.

## Сеть по умолчанию

Без явных настроек контейнер получает собственный network namespace и подключается к bridge-сети Docker (`docker0`) — виртуальному свитчу на хосте с NAT наружу. Два контейнера в одной bridge-сети видят друг друга по имени контейнера как hostname (встроенный DNS Docker), но снаружи хоста контейнер недоступен, пока порт не опубликован явно:

```bash
docker run -p 8080:80 nginx
```

`-p 8080:80` создаёт правило проброса: запрос на `хост:8080` идёт в `iptables`/NAT и попадает на порт 80 внутри контейнера. Без `-p` порт открыт только внутри той же docker-сети.

## Что стоит унести с собой

- Образ — неизменяемые слои; контейнер добавляет к ним один writable-слой и процесс. Удаление файла в слое не освобождает место в образе.
- Порядок инструкций в Dockerfile определяет, что попадёт в кеш — редко меняющееся (зависимости) ставится раньше часто меняющегося (код).
- Данные, которые должны пережить `docker rm`, обязаны жить вне writable-слоя — в volume или bind mount.
- Контейнер изолирует процессы и ресурсы (namespaces, cgroups), но не ядро и не архитектуру CPU — это не виртуальная машина.
